# Engines

Agneta doesn't run the agent loop itself. An **engine** does: an agent program that speaks ACP over stdio, calls the model, and calls tools. Agneta starts it in a sandbox, configures it for the session, and routes its stream to the app.

**Providers and engines.** Which engines can serve which kind of provider is one fixed table (`ProviderEngines`):

| Provider | Engines, most preferred first | Why |
| --- | --- | --- |
| ChatGPT plan | Codex | The plan's sign-in is Codex's own |
| Claude plan | Claude Code, Goose | The sign-in is Claude Code's own; Goose runs that same Claude Code |
| OpenAI API key | Goose, OpenCode, Codex | Any engine that speaks OpenAI |
| Anthropic API key | Goose, OpenCode, Claude Code | Any engine that speaks Anthropic |

- **The app picks** each task's provider and engine, among what its grant allows: the providers the user ticked, and the engines (all of them unless the user narrowed them: **Engines…** in the approval window, or Advanced in Settings → Apps). The pair must be in this table and on this Mac ([APP_PROTOCOL.md](APP_PROTOCOL.md#access)).
- **Sandbox modes.** Every engine can provide both modes, contained and developer access, except Goose on a Claude plan, which provides developer access only (`ProviderEngines.sandboxLevels`; [APP_PROTOCOL.md](APP_PROTOCOL.md#sandbox)).
- **The default** is the provider's, set per kind of provider in Settings → Engines (saved as `engine.<kind>`), else the most preferred one here; when the grant doesn't allow it, the first allowed one. A task that names no engine runs on it.
- **A resumed or forked task** always runs on the engine that saved it, which the grant must still allow.
- **Downloads.** An engine that downloads first (OpenCode, Claude Code's adapter, Codex's runtime in releases) starts downloading when it becomes a provider's default for a provider in use, or a task asks for it; tasks meanwhile are told to try again shortly (`-32015`, with the progress). Once installed, it's checked against its pin at each launch before it runs.

Accounts name no engine, and adding one asks nothing about engines.

**Adding an engine** takes three things: its adapter (`Sources/AgnetaKit/Engine/*Adapter.swift`), its row in `ProviderEngines`, and its entry in `EngineSource.all` (`Sources/Agneta/EngineLibrary.swift`: how it gets onto this Mac and how Settings describes it). `AccessTests.theTableIsWhatTheAdaptersAccept` fails until the table and the adapter agree on which providers it serves.

Everything an engine does its own way lives behind one adapter (`Sources/AgnetaKit/Engine/*Adapter.swift`, protocol `EngineAdapter`): how it starts and what its sandbox must allow, the shape of `session/new` and `session/load`, how instructions and steering are sent, how a tool's identity is read, how a conversation is exported for a fork, and where per-call usage is recorded. Apps see one contract; the `capabilities` on each session say which extras its engine has ([APP_PROTOCOL.md](APP_PROTOCOL.md#the-result)).

## Goose

[Goose](https://github.com/aaif-goose/goose) (Apache-2.0) is ACP-first: `goose-acp` is a small Rust binary for both Mac architectures with no telemetry or updater. One process can serve many sessions, because its per-session settings travel over ACP.

- **Isolation.** A private home (`HOME`, `GOOSE_PATH_ROOT`), an explicit environment with nothing inherited, `GOOSE_TELEMETRY_OFF`, `GOOSE_DISABLE_KEYRING` (credentials come from Agneta), session naming off, and mode `approve`, so tool permissions are asked rather than assumed. No user extensions, skills or recipes are loaded. Goose's own skill step is part of every agent, though: every session is offered `load_skill`, with Goose's built-in skills (goose-doc-guide, web-search) and any in the workspace's `.agents/skills`, `.goose/skills` or `.claude/skills` listed in its system prompt (measured on 1.59.2, under every policy; the web-search skill's commands run through the broker like any other).
- **Model catalog.** Every start, Goose downloads the public model catalog from `https://models.dev/api.json` (6.7 MB) into its home, in the background; Goose 1.59.2 has no setting to turn this off ([`model_catalog.rs`](https://github.com/aaif-goose/goose/blob/v1.59.2/crates/goose/src/model_catalog.rs)). It sends nothing of the task's, but models.dev sees the request. OpenCode's equivalent is off (`OPENCODE_DISABLE_MODELS_FETCH`).
- **Tools per session.** `_meta.enabledExtensions` lists the app's MCP servers plus only the built-ins the policy allows: none for `app-only`; `tree`, `read_image` and `shell` for `read`; plus `write` and `edit` for `workspace`; with [`builtins`](APP_PROTOCOL.md#narrowing-the-built-in-tools), only the kept groups' (`read`: `tree`, `read_image`; `edit`: `write`, `edit`; `execute`: `shell`), measured on 1.59.2 against a stand-in model API. Goose's other extensions (subagents, to-do lists) are never enabled, but `load_skill` can't be turned off, so `builtins` without `skills` is refused, and so is any `builtins` on a Claude plan. Goose reads files through its shell (`tree` lists folders, `read_image` shows images), so `read` without `execute` is refused too. With a model API, every tool of the app's goes to the model with each request (measured on 1.59.2), so `agneta/appTools` changes nothing. On a Claude plan the model is Claude Code (below, Plans), which Goose hands the app's servers and its own environment: it defers them as on its own route, and with `agneta/appTools` `always` Agneta sets `ENABLE_TOOL_SEARCH=false` in that session's Goose (each has a process of its own on this route). Measured on 1.59.2 with Claude Code 2.1.326 against a stand-in model API: no app tool in the first request by default, all 35 with it.
- **Shell.** `GOOSE_SHELL` points at `agneta-shell`, which hands each command to Agneta's tool broker. The broker runs it under the session's stricter tool sandbox ([ARCHITECTURE.md](ARCHITECTURE.md#the-tool-broker)). Under `read`, commands can read the workspace but write only a scratch folder.
- **Instructions** go through `_goose/unstable/session/system-prompt/set`, replacing the system prompt or adding a named part.
- **Fork** exports the source conversation (`_goose/unstable/session/export`) and imports it into a fresh engine.
- **Deleting a task** on the shared engine asks it to delete the session (`session/delete`, which 1.59.2 advertises). Its rows go, but the words stay in the database's free pages and its WAL log, so Agneta then checkpoints, vacuums and checkpoints again (`GooseAdapter.sessionsDeleted`). Goose numbers a new session after the highest id left, so deleting the newest frees its id, and an id once closed fails as "Session not found" for the rest of the process: the router never uses a session the process was asked to delete and asks for another (`Router.freshSession`). All three were measured on 1.59.2 and are covered by `RouterIntegrationTests.deletingATaskDeletesItsConversationInASharedEngine`. A conversation not deleted at once (Goose missing, failing or not answering within 10 s, Agneta quitting) stays on a list in Agneta's records and is asked for again at launch and after each clear (`AgnetaRuntime.pendingConversations`, `ConversationQueueTests`). So does one Goose deleted while its database couldn't be cleared (another connection kept its log in use): it isn't taken as deleted while a file still holds its words, and only the clearing is tried again (`aConversationStaysQueuedUntilNoFileHoldsIt`, `aFrozenSharedEngineCantHoldUpDeletingAConversation`). A Goose that doesn't answer is asked nothing more in that pass: the rest wait for the next. Before asking, Agneta reads Goose's database (read-only, only the measured schema, version 18; a missing database or another schema can't tell) and doesn't ask for a session none of its tables has, and after a delete that failed it reads again: so a delete Goose finished after Agneta stopped waiting isn't asked for again, which Goose would answer with -32603 "Session not found" (`GooseAdapter.sessionsStored`).
- **A provider's settings change** (its model, key, endpoint or default model and effort): the account's shared Goose stops, at once when idle or when its last session ends, so the next session starts one with the new setup (`EngineSupervisor.renew`). A running Goose keeps its `GOOSE_MODEL` otherwise.
- **Usage.** Goose's session database (SQLite, read-only) has one `usage_ledger` row per model call, with cache tokens and cost, and every message as the model saw it. The schema is Goose's own and is read by a reader pinned to this version; a mismatch is reported in the trace, not guessed at.
- **Plans.** Goose serves Claude plans, not ChatGPT plans (those run on Codex). A Claude plan uses Goose's `claude-acp` provider, which runs the downloaded `claude-agent-acp` with your installed Claude Code (`CLAUDE_CODE_EXECUTABLE`) under the account's own Claude Code configuration folder.
- **On a Claude plan, Goose is uncontained by the policy, and says so.** The Claude Code Goose runs as its model uses all its own tools (measured on 2.1.325: Bash, Agent, Skill, Workflow, Monitor, RemoteTrigger, WebSearch) and the claude.ai account's connectors; Goose's own brokered tools don't reach it. Agneta's engine sandbox still holds it to the session's folders, but the policy's tool, network and approval rules don't apply to those tools. It stays offered, as a choice: the access report lists it in `uncontained`, and Settings → Engines says what it means. So it provides developer access only (`sandboxLevels`): a contained task on it is refused, with why. For a Claude plan under Agneta's policy, run Claude Code directly.
- **Retries.** Goose retries a provider's 429 itself before the turn fails (about a minute).
- **Cost while a turn runs.** Goose writes a model call's `usage_ledger` row when the call ends, and Agneta reads it at its next 2-second poll: measured on 1.59.2 against a local model, 0.8 to 2.1 seconds after the call ended (`LimitMeasurementTests`). That, plus the watchdog's half second and the 10 seconds an engine has to stop after a limit cancels its turn, is how far past an app's spending limit each of the app's running turns on Goose can go. A model Goose has no price for (a local one) reports no cost at all: under a spending limit such a turn is marked `unpriced`, not counted.

The `_goose/unstable/*` methods can change with any Goose release, so the engine is pinned and these calls are tested at every version change.

## OpenCode

[OpenCode](https://github.com/anomalyco/opencode) (MIT) has a broad provider catalogue. `opencode acp` speaks ACP by starting a private `opencode serve` and translating to its HTTP API, which it keeps to itself. Over ACP, per-session instructions, permissions and MCP settings can't be set, and `_meta` isn't passed through. OpenCode reads its whole configuration per process, so **every OpenCode session gets its own process**, configured at launch through `OPENCODE_CONFIG_CONTENT`:

| Need | Configuration |
| --- | --- |
| Instructions | An `agneta` agent whose system prompt is the session's instructions, selected right after `session/new`. An app can't switch to another agent (`session/set_mode` or the `mode` option is refused with `-32602`): it would drop the instructions |
| Only what the policy allows | Permission rules: deny everything, then allow the app's tools (`<server>_*`), read tools for `read`, edit and shell for `workspace`, each only if [`builtins`](APP_PROTOCOL.md#narrowing-the-built-in-tools) keeps its group; `ask` instead of `allow` when the app decides (`ask-app`). Web fetch and search, subagents (`task`) and to-do lists stay denied (measured on 2.3.0: the model's list is `read`, `glob`, `grep`, `edit`, `write`, `opencode_worktree_remove`, `shell` and `skill` under `workspace`, and each narrowing removes its own) |
| The app's MCP servers | `mcp.servers.<name>` with the bearer headers, called directly (`codemode: false`); every tool goes to the model with each request (measured on 2.3.0), so `agneta/appTools` changes nothing |
| Shell through Agneta's broker | `shell: <agneta-shell>` |
| Nothing from the user | A private `HOME` and `XDG_*`, project config off, Claude Code integration off, model catalogue fetch, updates, sharing, plugins, LSP, formatters, snapshots and file watching off |
| No extra model calls | Session titles off (otherwise one extra model call per session) |
| Per-call usage | `OPENCODE_DB` in the engine home: `session_message` rows with model, tokens (cache included) and cost, one per step |

Its sandbox may listen on loopback, for the private server only.

**Usage, step by step.** Measured on 2.3.0: each step (a model call, and the tools it called) gets its assistant row when it starts, without tokens; its tokens, cost and `time.completed` are filled in when it ends, after its tools ran. Agneta reads a row once it's complete (or a later row shows it ended): reading it at the start lost that step's usage, and before this fix a two-call turn recorded one call. A step's row reached Agneta 0.7 to 0.9 seconds after its tools ended (`LimitMeasurementTests`), so under an app's spending limit each running turn on OpenCode can go past it by a step and its tools, plus the 10 seconds it has to stop. A model OpenCode has no price for costs $0 in its records: such a turn is marked `unpriced`, not counted.

**Known limits:**
- **Instructions between turns and fork** exist in OpenCode, but only through its HTTP API. They're not offered, and calls fail with `-32014`.
- **Plans** aren't offered on OpenCode: it keeps credentials in its own database and refreshes them itself, which would race Agneta's refresh of the same sign-in. OpenCode serves API keys.
- `skill` ignores permission rules and stays in the model's tool list. Skills come only from the private home, where there are none (skills planted in the workspace's `.opencode/skills`, `.agents/skills` or `.claude/skills` weren't found, measured on 2.3.0), so a session has no skill to load whatever its `builtins`. `opencode_worktree_remove` goes with `edit` (measured), and the sandbox keeps writes inside the workspace.
- OpenCode's "always allow" persists for the whole project; Agneta turns every "always" answer into "once".
- Tool names are `<server>_<tool>`, split at the first underscore, so an app's server name shouldn't contain one.
- The binary is about 238 MB (Bun).

## Claude Code

The user's own Claude Code, driven through [`claude-agent-acp`](https://github.com/agentclientprotocol/claude-agent-acp). The adapter's source is Apache-2.0, but its released binary embeds Anthropic's proprietary Agent SDK, so Agneta doesn't bundle it: it downloads the pinned release on first use and checks it against its SHA-256.

- **Finding Claude Code.** The Claude desktop app's bundled copies (`~/Library/Application Support/Claude/claude-code/<version>/…`) and command-line installs (`~/.local/bin`, `/opt/homebrew/bin`, `/usr/local/bin`, `~/.claude/local`), newest first. The user can pick one in Settings. The chosen executable is passed as `CLAUDE_CODE_EXECUTABLE`.
- **Accounts.** Each account has its own `CLAUDE_CONFIG_DIR` and temporary folder. A Claude plan signs in with your installed Claude Code's own login (`claude auth login --claudeai`, run in a hidden terminal). Without Claude Code installed, a Claude plan can't be added. Claude Code keeps the credential in the login Keychain, keyed by that folder, and refreshes it itself. Agneta never handles the plan's tokens. An Anthropic key is passed as `ANTHROPIC_API_KEY`.
- **Quiet.** `DISABLE_AUTOUPDATER`, `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC`, no settings from the user's own files (`settingSources: []`), no prompt suggestions, and MCP servers handed over at start rather than as command-line arguments, where other users of the Mac could read the bearer. The account folder's settings files (`settings.json`, `settings.local.json`, `managed-settings.json`, `CLAUDE.md`, `commands`, `agents`, `skills`, `hooks`) are read-only to its engines, and cleared before Agneta runs Claude Code itself (sign-in, status, sign-out).
- **Tools.** The exact built-in set by policy, passed as the SDK's `tools` (Claude Code then offers only those; measured on 2.1.325): `ToolSearch` in every set below (left out when `agneta/appTools` is `always`); nothing else for `app-only`; `Read`, `Glob`, `Grep` for `read`; also `Edit`, `Write`, `NotebookEdit` for `workspace`; with read or workspace tools also `Bash`, `TaskStop` and `Agent` (subagents), whose commands go through the broker (measured: a contained subagent's write worked and its `curl` couldn't resolve a name); Claude Code's own set under developer access, minus RemoteTrigger, Artifact, Projects, ClaudeDesign, SendUserMessage, SendUserFile and PushNotification (they reach the claude.ai account or devices) and Monitor and PowerShell (they'd run commands outside the broker). With [`builtins`](APP_PROTOCOL.md#narrowing-the-built-in-tools), the kept groups' tools only, contained and under developer access alike (`ClaudeCodeAdapter.developerTools`), as an exact list there too: measured on 2.1.326 through `claude-agent-acp` 0.107.2 against a stand-in model API, developer access with `read`, `edit` and `execute` offers `Read`, `Glob`, `Grep`, `Edit`, `Write`, `Bash` and `ToolSearch`, with `NotebookEdit` and `TaskStop` deferred behind it (all inline with `agneta/appTools` `always`), and no agent types or skills in the system prompt, where Claude Code's own set has `Agent`, `Skill`, `Workflow`, `ListAgents`, `SendMessage`, `ScheduleWakeup`, `ReportFindings`, web fetch and search, plan mode, schedules and worktrees, and lists its agent types and bundled skills. Names a version lacks are skipped (`TodoWrite` and `AskUserQuestion` on 2.1.326); its task-list tools, absent from its own set, are offered when `planning` is kept. `disallowedTools` names the code-running and account-reaching built-ins as a second net. Bash runs behind `CLAUDE_CODE_SHELL_PREFIX`, through the broker, never in the engine's sandbox (Claude Code runs commands it judges read-only without asking, so they must go through the prefix too). App tools appear as `mcp__<server>__<tool>`; the `tools` list doesn't touch them (see App tools, next). Claude Code's own sandboxed tools are an MCP server of its own (`mcp__workspace__…`), so an app's server can't use that name (the adapter's old client-backed `mcp__acp__…` tools went in its 0.18.0).
- **App tools.** Claude Code's tool search defers every MCP tool by default: the model's first request carries a `defer_loading` placeholder and the tools' names in a message saying to load them with `ToolSearch` (`select:<name>,…`), never their descriptions or schemas; the model loads each before its first call. Measured on 2.1.326 through `claude-agent-acp` 0.107.2, against a stand-in model API and app server: with 3 tools as with 35 (there is no threshold by default), with `app-only` and `read` tools, and behind a gateway too (on by default there since 2.1.304, Claude Code's docs say). With `agneta/appTools` `{"load": "always"}`, Agneta sets `ENABLE_TOOL_SEARCH=false` in the session's `options.env` (the adapter merges it over the engine's environment) and leaves `ToolSearch` out of `tools`: then all 35 tools, with their descriptions and schemas, are in the first request, with no placeholder and no tool search beta, a server 4 s slow to start included (the session waits for it). Two other ways were measured and not used: leaving `ToolSearch` out of `tools` alone also loads them up front but keeps the placeholder `defer_loading` entry, and `ENABLE_TOOL_SEARCH=auto` loads them below its threshold (10% of the context window) while still telling the model they're deferred. A server's own `alwaysLoad` or a tool's `_meta["anthropic/alwaysLoad"]` aren't passed on: the adapter keeps only an HTTP server's URL and headers.
- **Mode.** The adapter starts sessions in `auto`, where Claude Code decides its own permissions and asks nothing (measured on 0.107.2), and ignores `permissionMode` in the options. Every opened session is set to `default` with `session/set_mode`, a resumed one included.
- **The same options on every open.** Given no options, the adapter loads the workspace's `.claude/settings.json` (measured: a planted hook ran on resume). New, load and fork all send `settingSources: []`, `strictMcpConfig`, the tools, the environment (`agneta/appTools`) and the instructions.
- **Permissions.** Claude Code runs its own tools inside Agneta's engine sandbox, which can reach port 443 for the model. So Agneta checks every permission request against the policy first, by kind and by the tool's name (from the earlier tool call update): fetches are refused while the network is `none` (Bash passes: its commands run through the broker, under the command sandbox), and `other` passes only for tools known to run nothing. Under developer access everything passes, inside the widened sandbox. Only the `default` and `plan` modes are allowed; modes that stop asking (`acceptEdits`, `auto`, `bypassPermissions`) are refused.
- **Other tasks stay private.** The account's `projects/` folder, where Claude Code keeps every session's transcript, is denied to the engine, except the current session's own folder.

**Usage.** `emitRawSDKMessages` makes the adapter send `_claude/sdkMessage` notifications for assistant messages and results.
- Each assistant message is one model call, with its id, model, input and cache tokens exact, a subagent's with its `parent_tool_use_id`. **Its output count isn't:** it's the count at the start of the stream, repeated for every content block. On a two-call tool turn on Haiku, the per-call rows held 37–40 output tokens against 210–230 in the turn's result.
- **Each call's final usage comes from Claude Code's session transcript:** `projects/<the folder>/<session>.jsonl` in the account's `CLAUDE_CONFIG_DIR`, and `<session>/subagents/agent-<id>.jsonl` for its subagents. Each content block is a line with the message's id and its final usage and stop reason, all written together about 100 ms after the call ends (measured on 2.1.326 with 0.107.2, against a fake Messages API whose calls paused between blocks: the stream gave 2 output tokens, the transcript 321). That's during the turn for every call but the last, whose lines land 10–25 ms after the prompt's result. A resumed session (`session/load`, in a new process) appends to the same file, and its history isn't sent again as SDK messages (measured). A line without a stop reason (a call cut off) holds the opening count and isn't used.
- So the stream's row for a call is held back until its transcript lines are read (every 2 s while a turn runs, and every 25 ms for up to 1 s at its end, waiting only for each agent's latest call), then recorded once: final, `outputPartial: false`, `basis: engine-transcript`. A call the transcript doesn't give in time (5 s after the next call in its agent began, or by that 1 s) is recorded from the stream, `outputPartial: true`, `basis: engine-stream`. Held calls count toward `maxTurns` (model calls) at once. A turn that was cancelled, failed or stopped by a limit isn't waited for: its last call, cut off, never gets a final line. A session ended mid-turn records what was still held.
- **Without a transcript** (moved, not written, a resumed session under another name), a call given up on with nothing read since it began stops the holding: later calls are recorded from the stream at once, and turns don't wait, until the transcript gives rows again. A missing transcript costs one late call, not every call and turn.
- **The session's folder is the engine's to write, so it's read as untrusted.** Every path component below `projects` is opened without following links or leaving its device, and only regular files are read (not a FIFO, which would block, a device or a link to another task's transcript). A file is opened only when its size changed. Each read takes at most 4 MB of a file and 32 MB in all, from the first 256 subagent files by name (of at most 4,096 entries looked at), and decodes at most 4,096 assistant lines, duplicates included (65,536 calls in all; a trace record says when a cap was hit). Unfinished lines held between reads stay under 32 MB together, and a line longer than 16 MB is dropped to its end. Files no longer listed are forgotten, and one replaced by a shorter file is taken as read; a file there when a session was resumed starts again where it stood then. The session id must be a UUID. The project folder named after the workspace is looked in first, the others if it isn't there. On resume, the files are skipped to their ends by size, without reading them. Planted files can hide or forge a subagent's calls, as the engine could by writing lines: the numbers are as trustworthy as the engine. Only lines that can be assistant messages are decoded.
- Each result carries `modelUsage`: the session's running totals per model, side calls included (a session title, for one: no transcript lines), with a list-price `costUSD`. Agneta takes each turn's share of those totals as the turn's ledger (`basis: engine-turn-totals`) and keeps the per-call sums beside it as `callLedger`.
- The adapter's `stream_event` messages would also give exact output, but they come once per token, so they aren't used.
- Cost arrives only at the turn's end, so `maxCostUSD` can't stop a turn in time and is refused for Claude Code. An app's spending limit is checked before each turn and task instead, so a turn on Claude Code can go over it by one turn for each of the app's running tasks. When the turn-end cost lands relative to the prompt's result on an Anthropic key hasn't been measured yet: it needs an account this measurement didn't have.

## Codex

The user's own Codex (`codex app-server`), driven through [`codex-acp`](https://github.com/agentclientprotocol/codex-acp) (Apache-2.0), with a pinned Node runtime. Development builds bundle both; a release downloads them together, as Codex's runtime (`Agneta-codex-runtime-<version>-<arch>.zip`, attached to the release and pinned by the app's `codex-runtime.lock`), the first time a task runs on Codex.

- **Finding Codex** works as for Claude Code (`~/.local/bin`, `/opt/homebrew/bin`, `/usr/local/bin`), passed as `CODEX_PATH`. Codex 0.166 or later is needed for the app-server schema the adapter uses.
- **Accounts.** Each account has its own `CODEX_HOME`, with a `config.toml` Agneta rewrites at every start: credentials in the login Keychain (keyring mode: "Codex Auth", keyed by that folder, never a file the engine's own tools could read; separate from the user's own Codex sign-in), update checks, analytics and feedback off, no network for sandboxed commands. Web search is off (it runs on OpenAI's servers without asking) unless the session has developer access, where it's live, as in Codex. Off too are the features that would bring tools beyond the policy: the ChatGPT account's connectors (`apps`), plugins, browser and computer use, image generation, dependency installs, the background daemon and hooks. Checked against Codex 0.167. The files Codex trusts at start (`.env`, `AGENTS.md`, `AGENTS.override.md`, `skills`, `rules`, `prompts`, `hooks.json`, `hooks`) are cleared before each start and read-only to its engines; `config.toml` is rewritten. A ChatGPT plan signs in with `codex login` in that folder, and Codex refreshes its own sign-in. An OpenAI key is passed as `OPENAI_API_KEY`.
- **Modes.** Codex starts in `workspace-write` for `workspace` sessions and `read-only` otherwise. Developer access keeps `workspace-write`, so edits still ask. Only those two are allowed. `agent` ("Auto review") hands approval questions to Codex's own model reviewer instead of Agneta, and full access stops asking, so both are refused.
- **Instructions** are appended to Codex's own developer instructions (`systemPrompt` with `mode: "append"`). Replacing them would remove what tells the model how to use Codex's tools.
- **Its own tools,** measured on 0.167.0 through codex-acp 2.7.0 against a stand-in model API, with `app-only` and `workspace` tools: `view_image`, `apply_patch` (refused below `workspace` tools), its multi-agent tools, goals, questions for the user and (on gpt-6.1-sol's code mode) the clock's sleep, with its bundled skills (imagegen, openai-docs, skill-creator, skill-installer) listed in its instructions; Agneta's shell beyond `app-only`; web search under developer access. Codex's own shell is off in every session (`CODEX_CONFIG`): an `app-only` session, which had no settings of its own, was offered `exec_command` and `write_stdin`. [`builtins`](APP_PROTOCOL.md#narrowing-the-built-in-tools) turn off each group left out in the session's `CODEX_CONFIG`: `view_image` (`read`), `web_search` (`web`), `multi_agent` and `agents` (`subagents`), the bundled skills (`skills`), goals, sleep and questions (`planning`); without `execute` the session has no shell and isn't told of one. Each was measured gone from the model's tools, on the code-mode and plain-tools models alike. `apply_patch` has no setting, so `builtins` without `edit` under `workspace` tools is refused (under `read` tools it's listed too, and Agneta refuses each call). Codex reads files only through its shell, so `read` without `execute` is refused beyond `app-only` tools. Built-in tools' names for answering permission requests come only from `_meta.codex.toolName`, never a call's title, which for a command is the command the model wrote; codex-acp 2.7.0 doesn't send that field (measured: a built-in call such as `spawn_agent` arrives as kind `other` with the title `spawnAgent` and its input, `view_image`, goals and questions send no tool call at all, and a permission request carries only the call's id and kind). So Codex's requests are judged by kind: under `builtins` one of kind `other` or `think` is refused, and without them nothing changes. Measured too: `spawn_agent` ran without a permission request, so only turning the group off (`multi_agent`) keeps subagents out.
- **Tools.** App tools appear as `mcp.<server>.<tool>`. Edits ask permission first and work (`apply_patch`).
- **App tools are deferred** on every model in Codex's catalog, its default `gpt-6.1-sol` included: each has Codex's tool search (`supports_search_tool`, all twelve in 0.167.0's), and Codex then defers every MCP server's tools, so the first request names only "Deferred tool namespaces: mcp__app" and the model finds the tools when it needs them. By the same rule Agneta's own shell server (`mcp__agneta`) is deferred too, and `always` leaves it so: it isn't the app's. A model outside the catalog gets them up front (measured: `gpt-5.1-codex`, one `mcp__app` namespace with every description), which is what an earlier measurement here saw. With `agneta/appTools` `always`, Agneta names each of the app's servers in `features.code_mode.direct_only_tool_namespaces` in `CODEX_CONFIG`, as Codex names their namespaces: `mcp__` and the server's name with every character but an ASCII letter, digit or `_` made `_` (measured: `my-app` is `mcp__my_app`, `a.b` is `mcp__a_b`; two servers that come out the same get a hash suffix from Codex and aren't named, so give your servers distinct names), which bypass deferral (in Codex's own words for the setting): then all 35 tools, with their descriptions, are top-level in the first request. Both measured on Codex 0.167.0 through `codex-acp` 2.7.0 with `gpt-6.1-sol` and Agneta's `config.toml` features, against a stand-in model API and app server; a ChatGPT plan's own model list (fetched from OpenAI) wasn't, but the setting doesn't depend on the model. Codex 0.166.0, the oldest Agneta runs, wasn't run, but its source has the same setting, name rule and deferral code. Codex's `code_mode_only_strict_3p_tools` feature would defer them anyway: it's off by default, and pinned off in Agneta's `config.toml`.
- **Usage** comes from Codex's rollout files in `CODEX_HOME/sessions`: one `token_usage_record` per model call, with the response id and cached tokens. They carry no cost, so an app's spending limit can't count Codex: while one is set, the app's tasks on an OpenAI key don't run on Codex ([APP_PROTOCOL.md](APP_PROTOCOL.md#limits-the-user-sets)). On a ChatGPT plan nothing is counted, and Codex runs as always. On a ChatGPT plan, the same files carry the plan's own limits (used percent, window, reset), which Agneta shows in its menu.

**Commands go through Agneta's broker.** Codex runs its own commands without asking and wraps each in its own `sandbox-exec`, which macOS won't nest inside Agneta's sandbox (measured: `sandbox_apply: Operation not permitted`). So Codex's own shell is off (`shell_tool`, `unified_exec`), and its commands run through Agneta's own MCP shell instead: `agneta-shell --mcp`, the `shell` tool of the `agneta` server (`mcp__agneta__shell`), set in the account's `config.toml`, under the session's command sandbox. The session's instructions say so. An app's tool server can't be named `agneta` or `codex_apps`.

## Adding an engine

An engine is one type that implements `EngineAdapter`. Start from the closest existing adapter, and test it with the scenarios in `Tests/AgnetaKitTests` (`AppScenarioTests` is parameterized by engine). Declare what it can do in `capabilities` honestly: a feature the engine can't do is refused with `-32014`, never faked. Anything that would let the engine act outside the policy (a mode that stops asking, a tool outside the sandbox) is refused in the adapter.
